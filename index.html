Can process sensors warn us before a unit fails final test?

A time-aware study of the SECOM semiconductor dataset: what we asked, what the data looked like, how we built and judged the models, and what the evidence does and does not support.

QuestionDataPreprocessingModelsEvaluationResultsError analysisLimitationsRepository

Question. Can the process-sensor readings recorded for a production unit predict whether it fails final testing?

Answer. Weakly, yes. Our chosen model ranks failures better than random (PR-AUC 0.227 against 0.054 for random), but with only 17 test failures the size of the gain is very uncertain.

Try it. Flag the top N units and see who it catches.

1. The question and what a row is

  • One row is one production unit, described by 590 sensor readings and a timestamp.
  • Target: failed (1) or passed (0) the final quality test.
  • When a prediction is made: after the process sensors are recorded and before final testing, so only those readings are used.
  • Claim limit: we claim predictive association within this one historical dataset, not that any sensor causes failures or that it transfers to other fabs.

2. The data

SourceSECOM dataset, UCI Machine Learning Repository (CC BY 4.0). Public; two files: sensor values and labels with timestamps.
Size1,567 units × 590 sensors; 104 failures and 1,463 passes (6.6% fail); 19 July to 17 October 2008.
Variables590 anonymized numeric sensors (f0 to f589), a pass/fail label, a timestamp. Sensor meanings are not documented.

Quality issues that shaped our choices

Sensors by missingness

52 complete, 510 partly missing, 28 more than half missing

Units by outcome

1,463 passed, 104 failed

  • Heavy missing data. 538 of 590 sensors have gaps and every unit has at least one. Some sensors go missing together (for example f157, f158, f292 and f293 are all 91.2% missing), which suggests a measurement step that was not recorded.
  • Constant sensors. 116 sensors never change and carry no information.
  • Mixed scales. Readings range from about 1 to over 3,000.
  • Rare failures. Always guessing “pass” is right 93% of the time, so accuracy is not informative.
  • Drift. The weekly failure rate falls from above 20% in the earliest weeks to a few percent later, so the process changes over time.

3. Preprocessing and why

Every step is learned from training data only, inside one scikit-learn pipeline that is refit on each training block, so nothing from validation or test data leaks in.

StepWhy
Fill gaps with the training medianEvery unit has a gap, so we cannot drop units. The median resists extreme sensor values.
Drop constant sensorsThey carry no information (116 of 590).
Standardize each sensorScales differ by orders of magnitude; unscaled sensors would dominate the model and the selection scores.
Keep the top k sensors by an F-score590 sensors against 87 development failures invites fitting coincidences. We chose k = 10 (see below).
Class weights, not resamplingMistakes on the rare failures count more during training; no synthetic units were created.

4. Baseline and models compared

  • Baseline: majority class. Gives every unit the same score, so its PR-AUC equals the failure rate. It matched the failure rate in every fold, which confirms the code is correct.
  • Logistic regression (our chosen model). A weighted sum of the selected sensors turned into a failure probability; a penalty (C = 0.01) keeps weights small so it does not memorize noise. Simple, stable with few failures, and the weights can be inspected.
  • Random forest. Many decision trees on random subsets, averaged (300 trees, k = 100). It can learn interactions between sensors that a weighted sum cannot.

Selection rule, fixed before testing: prefer the simpler model unless the complex one is clearly better, and among settings within 0.01 of the best mean gain take the simplest. This gave logistic regression, C = 0.01, k = 10.

5. How we evaluated

Units were split by time, not at random, because the process drifts and a real prediction is always about future units. The last 20% was locked away and used once.

Eleven validation failures is too few to choose between models, because one unit shifts recall by about 9 points. So we merged train and validation into a development set (87 failures) and compared models with expanding-window time-series cross-validation: always train on the past, validate on the next block.

  • PR-AUC summarizes the trade-off between catching failures (recall) and false alarms (precision) over all thresholds. Random ranking scores about the failure rate, so we always report the gain over that baseline.
  • Recall in the top 10% of units answers a practical question: if engineers can inspect only that many units, how many failures do they find?
  • Uncertainty: a bootstrap that resamples whole days (2,000 rounds), because failures arrive in bursts and resampling single units would be falsely confident.

7. Error analysis

  • On Oct 3, a day with no failures, the logistic model placed 12 of its top 32 flags. Its scores seem to partly follow day-level process conditions, not only single units.
  • Its best catch was an isolated failure on Oct 15, ranked first of 314. Five failures ranked in the bottom half of its scores (ranks 180 to 295), so some failures are not visible in the sensors it uses.
  • The forest ranked many failures moderately high but few at the very top, which is why it scores lower on PR-AUC and top-10% recall despite looking reasonable.
  • Which sensors matter? Across the five folds, 30 different sensors were chosen from 50 selections; none was chosen in all five and eight in at least three. The steadiest ones are near-duplicates (f430, f431, f434, f435 and f436 correlate at 0.91 to 1.00), so they carry about one signal. Two sensors in the final model (f129, f510) were never chosen in any fold.

8. Limitations

  • Only 17 test failures, in about nine separate events, so every number is uncertain.
  • The process drifts, so performance in a later period may differ.
  • The sensors are anonymized: we can say which readings carried signal, not what they measure, and results show association, not cause.
  • Cross-validation folds overlap, so the sensor stability above is probably optimistic.
  • The forest and logistic regression used different numbers of sensors (100 and 10), so that comparison mixes model and setting.
  • The test set was used once, so no tuning came from it; we did not test other model families such as gradient boosting.
